# Action truth within the work boundary

Check changed or unverified consequential actions; reuse unchanged verified contracts. First identify what the declared artifact must actually demonstrate:

| Work type | Trace and proof |
|---|---|
| Prototype | Visible claim → local handler → actual local/simulated effect. Test claimed local storage/recovery; label unsupported production destinations once. Do not require a server to select a composition. |
| Production | Visible claim → handler/request → validation/authorization → stored state/read model → downstream effects → visible readback. Verify relevant failed/uncertain responses and retry safety. |
| Research | Check the source and scope supporting the action claim. Distinguish documented behavior, observed interaction and proposed behavior; do not perform live actions just to research them. |

Distinguish **saved, linked, published, publicly visible, notified, queued, sent and delivered**. A toast or successful request can demonstrate acceptance without demonstrating delivery. Local success must name its scope and survive the recovery the artifact promises. Never silently broaden an attached item's audience.

For material uncertainty, record only the relevant fields: `action | stores/links | publishes where/to whom | sends/notifies | third parties | defaults | eligibility | failure/retry | evidence`. Unknown effects remain unknown. These fields are prompts, not a required table for every button.

Treat audience summaries, saved indicators, counts, disabled reasons and next-step sentences as factual claims. Before a risky action, make who/what it affects clear. A surprising default is evidence to investigate; changing policy still requires product authority.

Test uncertain confirmation before recommending a retry that could duplicate effects. Use synthetic or authorized data; never send messages, expose private content or weaken authorization just to obtain design evidence.
