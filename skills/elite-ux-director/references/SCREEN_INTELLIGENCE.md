# Screen intelligence: a bounded working sheet

Read current project authority first. Follow a declared adapter link if present, selecting only the target surface. A stale adapter is a lead, not canonical truth. Reuse an existing brief/ticket; this table is not a mandatory new artifact.

| Question | Record only what changes this decision |
|---|---|
| Job and people | Actor, goal, context, permission, affected parties; persona evidence level |
| Screen truth | Route, current branch/version, role, real vs synthetic data, screenshot/state |
| Data | Canonical entity, derived state/read model, loading/error/empty behavior, freshness |
| Action | Visible label, handler, endpoint/service, eligibility, authorization, persistence |
| Consequences | Save/link/publish/notify; audience, public/third-party destinations, defaults, retry |
| Existing system | Reusable components/composables, tokens, variants, semantic DOM constraints |
| Constraints | Approved composition/locks, current task scope, assets, supported devices |
| Memory | Latest relevant accepted/rejected concepts, who decided, reasons and evidence |
| Unknowns | Specific missing fact, smallest check to resolve it, safe interim behavior |

Search route/component → composable/handler → endpoint/controller → service/policy/side effects. Avoid whole-repository reads. A service API name alone does not prove authorization. Request only missing information that materially blocks the decision.

Generate a state list from data and transitions, not every theoretical combination. Mark unavailable states and fixtures explicitly; do not manufacture eligibility or perform real sends merely to obtain screenshots. Screen intelligence can remain five concise bullets for a small change.
