# Research develops design intelligence

The intended cycle is **read and study → extract principles → develop design intelligence → improve the skill → test on real designs → gather feedback → refine**.

Routine implementation normally uses the compact learned workflow, current product facts and targeted practical references. It does not load book catalogs, K-cards, homepage machinery or every design skill. The full corpus and its reading history remain preserved; absence from the runtime path is not devaluation of research.

## On-demand routes

- Personas or context uncertainty: PERSONA_AND_CONTEXT_METHOD.md.
- One unresolved UX mechanism: TASK_SOURCE_ROUTER.md, then at most one or two relevant decision/knowledge cards, using scripts/retrieve.py if helpful.
- Explicit source study: BOOK_STUDY_PROTOCOL.md, VISUAL_ANALYSIS_PROTOCOL.md and, for a genuine conflict, CROSS_BOOK_SYNTHESIS.md. Keep SOURCE_LEDGER.md access limits.
- Substantial visual question in the Lab: existing interface-atlas and handbook/VISUAL_DIRECTION_TASK_ROUTER.md; scripts/prepare_design_packet.py can select a bounded set. Read the actual images before transferring mechanisms. These Lab paths are optional repository resources, not dependencies of the standalone skill.

## Promotion gate for skill development

Record the question, original source/edition/passage and access status; separate source claims from interpretation. Extract a conditional mechanism with counterexample, failure modes and a proposed test. Compare it against existing guidance; revise or remove overlap instead of adding another universal rule.

Promote only what changes a decision or observable reasoning, creative judgment or design outcome. Use realistic authorized designs and distinguish activation, technical verification, critic/owner verdicts and actual user outcomes. Preserve failed transfers and contradictory evidence. Never claim a book was read because indexed, a persona was interviewed because generated, or a saved principle changed model weights.

Claude field feedback on v0.5 is valuable REPORTED evidence, not a controlled causal study. The v0.6 changes address specific observed/reported failure modes; validation of packaging and capture checks cannot establish general design superiority.

Larger corpus ingestion, new evaluation services, automatic research pipelines and new Atlas infrastructure belong to a future Lab phase. Do not build them as part of ordinary product work.
