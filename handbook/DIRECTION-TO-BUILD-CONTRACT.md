# Design Direction to Frontend Build Contract — v0.1

Purpose: communicate source-backed creative intent to an implementer without micromanaging its frontend coding skill.

## Input required
- Audience, situation and essential job
- Verified product content and allowed image/assets (unknowns explicit)
- One-sentence concept thesis (not a palette)
- Information hierarchy and primary action
- Two to four source-backed mechanisms with exact URLs and evidence tags
- Three distinct art-direction candidates and reasoned selection status
- Fixed behavior / permitted visual variation
- Accessibility, responsive, motion, performance and stack constraints
- Specific clichés and copying risks worth challenging
- Acceptance criteria and screenshot/test evidence to return

## Builder report required
1. Real repo/environment examined and key constraints.
2. Reading of the thesis and contradictions.
3. Implementation structure and rationale.
4. Files changed, dependencies and commands.
5. Actual evidence: viewports, focus, keyboard, reduced motion, loading/errors and browser results.
6. Departures from direction and reasons.
7. Unverified issues and suggested next review.

## Design review failures
- Subject mismatch: concept could be reused for any unrelated app.
- Cliché convergence: stylistic defaults have no contextual justification.
- Hierarchy mismatch: product purpose or action buried.
- Expression/usability conflict: narrative prevents a task.
- Implementation drift: code no longer embodies the creative thesis.
- Evidence inflation: screenshots/tests or performance claims imagined.

## Authority
Explicit owner decision -> authorized design brief -> real project constraints -> accessible behavior -> source-grounded design mechanics -> nonbinding skill heuristics.

Final Faneqo evaluation remains an isolated homepage mockup, only when Claude is available and the user approves its implementation.
